**原則**: 大きな仕様は実装前に計画させ、設計を問い詰めてから任せる。指示は手順ではなく目的・方針・止まる条件で書き、細部は遊び手の体験を基準に任せる。見た目は文章でなく実物を見て決める。

## なぜ

- AI が先走ると責務違いの不適切な変更が混ざり、戻す手間がかかる（ADR-0025）
- 「あいまいなまま計画がすすんでいるように思えるので、十分な分析のもと実装に移ります」（ADR-0122、本人の発言）
- 「詳細なやるべきことを書くより目的を明確にすることの方が重要」「厳密であるが故に、変更が非合理性を持つこともある」（ADR-0108、本人の発言）
- 細部を投げられると設計を丸投げされた形になる（ADR-0162）
- 文脈を引きずった AI は自分の案を良いと思い込みやすい。見た目の判断は質問より試作が速い（ADR-0173・ADR-0119）

## 規則

| 規則 | 範囲 | 根拠 |
| --- | --- | --- |
| 実装依頼は「まず計画から」と区切り、「計画して」「調べて」と頼んだときは編集させない。コードは極力短く、既存の Root は触らずに足す | 全体 | ADR-0025 |
| 大きな仕様は実装前に grill-with-docs で精査してから実装に移る。設計未確定の新機能でだけ 1 行提案する | 全体 | ADR-0119, ADR-0122 |
| 大きな計画は「決定を集める企画サイト → AI 向け指示書 → 実装」の 3 フェーズで進め、要決定が全部埋まってから指示書に変換する | Idle-MInertia | ADR-0091 |
| 指示書は目的・方針・完了の判断と止まる条件だけを短く書き、文書の性格の説明や弁明は削る | 全体 | ADR-0108 |
| メインの AI は割り振りとレビューに徹し、失敗できない変更は複数エージェントの観点別レビューを通す | 全体 | ADR-0073 |
| 本人に聞いてよいのはテーマ・世界観・体制・予算・大きな捨て選択だけ。細部は担当が決めて理由を 1 行添え、後から覆せるよう記録する | 全体 | ADR-0162 |
| アイデアを引き出す対話は「見立てを一文 → 短い確認の問い」で行い、選択肢の列挙・長い前置き・抽象すぎる問いは禁止 | 全体 | ADR-0037 |
| 試作は外部依存のない 1 枚の HTML で作り、採用したものだけを移植する。手触りの判断は質問より試作 | 全体 | ADR-0038, ADR-0119 |
| 絵作りは画面の領域に名前を付けてから指示し、模様は文章でなく描いた実物を見て選ぶ | Idle-Sphere | ADR-0127 |
| UI の作り直しは「参考画像 → Unity と無関係のデザイン → Unity で差をなくす」の順で進める | Idle-MInertia | ADR-0274 |
| 没になった AI の絵の案は全部消し、白紙のサブエージェントに作り直させる | Rootflux | ADR-0173 |
| 見た目の調整で AI が外し続けたら、全部戻させて自分で作った素材を当てさせる | Idle-MInertia | ADR-0165 |
| AI エージェントは役割ごとの組織（PM → Director → Engineers）にして任せる | Idle-Factory | ADR-0035 |

## 境界

- 課題管理システム前提のスキルは個人開発では空回りするので見送った（ADR-0119）
- AI の組織化（ADR-0035）の理由は文書に記載がない
- 根拠を自前の少数データで後付けさせず、見つからなければ「根拠がない」と言わせる（ADR-0142。「AI の手を止めない」参照）

**原則**: 動作と見た目の確認は、コードを読むことや数値の一致ではなく、Editor の Play と実機の画面で行う。確認のための仕掛け（上書き・診断・切り替え）は保存せず Editor に閉じ、使い終わったら消す。

## なぜ

- 数値の一致だけで「虹色になるはず」と判定し、画面で確かめていなかったのが誤りだった（ADR-0226）
- コードを読むだけでは、共有シートが読まれていないことに気づけなかった（ADR-0209）
- バッチモードの確認では見えない不具合が、Play で確かめると見つかった（ADR-0200）
- 手作業の往復が開発の律速になる（ADR-0159）
- 発売前フラグを一時的に書き換えて確認すると、戻し忘れで事故になる（ADR-0415）

## 規則

| 規則 | 範囲 | 根拠 |
| --- | --- | --- |
| Unity の確認はエディタを MCP で操作して Play で行うのを優先し、バッチモードは MCP が本当に使えないときだけ使う | Idle-MInertia | ADR-0200 |
| MCP が繋がらないときは、代替へ切り替える前に原因を調べて伝える | Idle-MInertia | ADR-0200 |
| Editor の起動・再生・撮影は人に頼まず、AI が Unity-MCP で自分で行う | 全体 | ADR-0159 |
| mcp-unity は作業フォルダから組の Unity を選ぶ起動スクリプト経由で起動する | 全体 | ADR-0195 |
| エディタを操作できないときは、バッチモードの使い捨て検証スクリプト（PASS/FAIL）と UXML の画像書き出しで確かめ、済んだら消す | Idle-MInertia | ADR-0202 |
| デバッグ機能は保存しない一時上書きとして専用クラス（DebugOverrides）に隔離し、Editor 専用で作り、使い終わったら消す | Idle-MInertia | ADR-0168 |
| 発売前の構成を確かめるときは const を触らず、リポジトリに入らない EditorPrefs の切り替えで「発売後」として振る舞わせる | Idle-MInertia | ADR-0415 |
| 別の PC の見た目の違いは推測せず、状態の出どころを 1 回で書き出す診断メニューで調べる | Idle-Factory | ADR-0222 |
| 見た目を確かめるための Play（最大サイズの根）は、セーブの進行によらず確認したい状態に固定する | Idle-Factory | ADR-0221, ADR-0226 |
| UI のつなぎ損ねは実機では黙って捨て、エディタでだけエラーを出す。縦横 UXML の名前はテストで照合する | Idle-MInertia | ADR-0361 |
| 確認に要る道具（mcp-unity パッケージ）はリポジトリに戻してよい | Idle-MInertia | ADR-0400 |

## 境界

- 確認用の Play は普段の Play とセーブに影響しない（ADR-0221）
- 「以降 Unity の操作は私が請け負います」と本人が引き取る場面もある（ADR-0328）
- 「画面の確認は自分が担当する」（ADR-0122）と、AI が Editor を操作する（ADR-0159・ADR-0200）は、どちらを採るか場面ごとに決まっている。線引きは未決

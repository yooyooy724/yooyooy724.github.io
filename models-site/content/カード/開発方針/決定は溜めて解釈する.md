**原則**: 開発の決定は ADR として溜め、遊び手の声と合わせて解釈し、デザインモデルとリスクリストに育てて次の開発に適用する。保管庫は「誰が書き換えるか」と寿命で区画を分け、文書は読むより見てわかる形で書く。

## なぜ

- 意思決定の履歴と遊び手の反応を、次の開発に効く形に圧縮する（ADR-0184）
- 寿命の違う情報を同じ場所に置くと記事空間の純度が崩れる（ADR-0060）
- 本人が長文を読むのが苦手で、重複は規則と実態のズレを生む（ADR-0105）
- 「タグだけを見て何が不足しているかを眺められる」（ADR-0204、本人の考え）
- 属さないタスクが出たらプロジェクトが 1 つ足りていないサイン（ADR-0103）

## 規則

| 規則 | 範囲 | 根拠 |
| --- | --- | --- |
| すべてのプロジェクトを「統計データと ADR を解釈 → モデルとリスクを育てる → 形式化して開発に適用」のサイクルで回す | 全体 | ADR-0184 |
| ADR は 5 軸（リスク低減度・時間的般化・空間的般化・独特度・マネタイズ貢献度）で評価する | 全体 | ADR-0184 |
| ADR の蓄積は MCP サーバーで自動化する | 全体 | ADR-0186 |
| デザインモデルは 1 原則 1 枚のカードにし、カテゴリのページをカード一覧にする。範囲は札、テーマはタグ | 全体 | ADR-0204 |
| デザインモデルとリスクだけは保管庫 git の外（github.io）に置き、人がサイト上で編集する | 全体 | ADR-0181 |
| フォルダは PARA ではなく「誰が書き換えるか」で分け、進行状態は status 欄で表す | 全体 | ADR-0182 |
| 保管庫は Wikipedia 的な記事だけを扱い、索引は作らずタイトル規則とリンク規則で整える | 全体 | ADR-0029 |
| 区画は図書館（記事）・Projects（進行中の仕事）に分ける | 全体 | ADR-0060 |
| タスクは必ずどれかのプロジェクトの文書に書く | 全体 | ADR-0103 |
| 文書は箇条書きと表を第一選択にし、段落は理由の説明にだけ使う。迷いや重複が起きてから階層を作る | 全体 | ADR-0105 |
| 開発ログと性能の決定ログは 1 つの変更・1 つの決定ごとに、理由と根拠（実測値）を添えて残す | 全体 | ADR-0077, ADR-0117 |

## 境界

- GTD 式のタスク置き場「営み」（ADR-0060）は 1 か月余りで器がほぼ空のまま、廃止した（ADR-0103）
- 「見てわかる」の規則をいつ誰が言い出したかは不明（ADR-0105）
- ADR-0001「決定の記録場所を分ける」は日付と評価が無く、根拠の表には含めていない

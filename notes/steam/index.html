Idle Minertia / Steam Release Plan

決めたことを、
実装できる計画へ。

モバイル版 Idle Minertia を Windows / macOS の Steam へ展開する。 このページは、フェーズ1で決定した方針と、これから行う作業をチームで共有するための実行計画です。

フェーズ1の議論を整理済み 次工程: フェーズ2の指示書作成 最終確認: クラウドセーブ方式
01 / DECISIONS

プロジェクトの前提

以降の設計と実装は、ここにある前提を変えずに進めます。

PLATFORM

Windows / macOS 同時対応

旧作の AppID 3217600 は使わず、本作用の AppID を新規取得します。

PRODUCT

F2P + Steam向けDLC

売上拡大を目的とし、Steamの文化に合わせて広告導線と商品を再設計します。

OPERATION

モバイル版も継続

同一コードベースで並行運用し、Steam対応によって既存ユーザーを壊しません。

QUALITY

期限より完成度を優先

単なる移植ではなく、横長・マウス・Steam機能を備えたPCゲームとして仕上げます。

SCOPE

1.0は原則すべて対応

例外はQWERT個別操作とフレンド内リーダーボード。これらは初回リリースから外します。

DELIVERY

小さなPRへ分解

フェーズ2で、1指示書 = 1PR相当の独立した作業へ変換します。

02 / ARCHITECTURE

モバイルとSteamの差分を境界に閉じる

既存APIを壊さず、新しいプラットフォーム層を上から被せます。

境界モバイルSteam
IRewardService既存広告処理へ委譲導線ごとの報酬・解禁条件
IStoreServiceUnity IAPSteam DLC / 所有権
ICloudSaveBackendFirestore REST最終確認後に確定
IAuthServiceGoogle / AppleSteam ID
IAchievementServiceNo-OpSteamworks実績
IReviewPrompt既存レビュー導線No-Op

変更しないもの

AdRoot.cs、Shop/IAP/、既存Firebase実装は直接書き換えません。新規実装から委譲します。

守る境界

#if はInstaller、プラットフォーム固有実装、Editor内部に閉じます。View / ViewModel / Domainへ分散させません。

UpgradeDomainを変更したらDLL反映が必須です。 ビルド済みDLLをUnityへコピーするまで、その修正はゲーム側には反映されません。
03 / WORKSTREAMS

領域ごとに決めたこと

各担当は、自分の領域だけでなく、前後の依存関係も確認してください。

SAVE / SERVER

セーブ互換性を最優先する

  • AES暗号化を有効化する
  • 平文セーブからのマイグレーションを必須とする
  • ACTkは見送り、メモリ・時計改ざんは残存リスクとして扱う
  • NetherCompanionはFirestore RESTで継続する

MONETIZATION

広告を消すのではなく商品を作り直す

  • 本線はデイリーダイヤ付与型DLC
  • 受け取り忘れを失効させず、複数日分をまとめて受領可能にする
  • RemoveAds効果は倍率 / ブースター / デイリー / 時間短縮に分ける
  • 不成立時は買い切り化し、課金要素を全廃する

UI / INPUT

縦UIの畳みを、横では1段だけ解く

  • 器のUXMLはVertical / Horizontalで分ける
  • 表示内容を持つ部品は共有する
  • V/Hのname集合を機械的に検証する
  • 全画面対応とリサイズ追従まで行う

PC OPERATION

マウスの手数を減らす

  • Shift+クリックで即時移動
  • ダブルクリックで可能な限り連続マージ
  • 右クリックで詳細、Ctrl+クリックで複数選択
  • 連続マージAPIはDomainに置き、既存オートマージと共有する

STEAM FEATURES

Steam版として必要な機能を揃える

  • 実績30〜60件。判定はDomain
  • リッチプレゼンスは最新Cave名 + 到達深度
  • オーバーレイ中もゲーム進行を止めない
  • フレンド内リーダーボードは初回リリース後

RELEASE / QA

配信は手動、確認は広く

  • Steamビルドのアップロードは手動
  • ストアページは英・日・中・韓・独・仏・西
  • ゲーム内13言語は維持
  • 解像度、DPI、リサイズ、オフライン、長時間放置をQA対象にする
04 / PHASE 2

決定を、実装指示書へ変換する

フェーズ2は再び仕様を議論する工程ではありません。決定を安全に実装できる粒度へ分解します。

1指示書に必要なもの

  • 目的と対応する決定事項
  • 触ってよい / 触ってはいけないファイル
  • Model / ViewModel / Viewの責務
  • 前提作業と依存関係
  • 受け入れ条件とテスト方法
  • DLL反映のタイミング
  • 失敗時のロールバック条件

最初に作る指示書

  1. プラットフォーム抽象化
  2. Steamworks.NET整理と初期化
  3. セーブ暗号化と移行
  4. 横長UXMLの1画面試作

各指示書は1PR相当とし、単独でレビュー・検証・ロールバックできるようにします。

05 / ROADMAP

実装は、この順序で進める

最大の未知数を先に検証し、土台から順に積み上げます。

  1. 検証ビルドを通す

    Windows StandaloneでDomain DLL、SteamAPI.Init()、横長での実際の崩れ方を確認します。ここが通るまで他の実装へ進みません。

  2. AppID取得を並行して開始する

    Steam Directの支払いと審査は、自分たちで短縮できない待ち時間です。

  3. Steamworks.NETとDefineを整理する

    二重導入を解消し、Steam固有コードがモバイルビルドへ混入しない状態を作ります。

  4. PCの基本設定とプラットフォーム境界を作る

    二重起動防止、フレームレート、インターフェース群、Editor用実装を整えます。

  5. セーブ、報酬、Steam機能を実装する

    セーブ移行、広告導線の置換、Steam Cloud、実績を、安全性の高い単位へ分けて実装します。

  6. 横長とPC操作を段階的に展開する

    1画面で方式を検証してから全画面へ広げ、最後にリサイズ追従と入力を完成させます。

  7. 商品、macOS、ストア、QAを仕上げる

    DLC、署名・公証、ストア素材、多言語ページ、実機・長時間テストを終えてリリースへ進みます。

06 / NEXT ACTIONS

チームが次にすること

この3点を終えると、フェーズ2の指示書作成を開始できます。

ACTION 01

クラウド方式を最終確定

推奨は、セーブをSteam Cloud、NetherCompanionをFirestore RESTに分けるA2です。二重同期は行いません。

ACTION 02

外部調査の担当を置く

デイリーDLCの可否、価格事例、Steam Cloud設定、macOS公証、ストア素材要件に担当者と期限を設定します。

ACTION 03

フェーズ2の指示書を作る

まず抽象化、Steamworks初期化、セーブ移行、横長1画面試作の4本を作成します。

実装開始の条件: フェーズ2の指示書と受け入れ条件をレビューし、フェーズ3最初の検証ビルドが通ること。

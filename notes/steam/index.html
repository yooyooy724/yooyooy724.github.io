1. 決定事項一覧

以降の設計と実装は、次の前提を変えずに進める。 変更が必要になった場合は、個別実装の都合で書き換えず、Steam移植全体の決定として再確認する。

論点決定実装への影響
対応OSWindows / macOS 同時対応macOS公証、Universal Binary、OS別Depotと実機確認を含める。
販売方式F2P + Steam向けDLCモバイル課金をそのまま移植せず、Steamの商品として設計し直す。
モバイル版継続して並行運用Steam対応で既存モバイル版を壊さない。同じドメインを使う。
品質と時期期限より完成度を優先日程だけを理由に設計やQAを削らない。
1.0スコープ原則すべて対応横長・PC操作・実績・リッチプレゼンス・多言語ストアを含める。
1.0の例外QWERTショートカットとフレンド内リーダーボード初回リリース後の追加対象として管理する。
開発単位小さなPRへ分解1PRで確認できる変更量とし、依存順に統合する。
AppID3217600は旧作用。新規取得Steam Directと審査を実装と並行して開始する。

2. アーキテクチャ方針

モバイルとSteamの差分は、呼び出し側へ条件分岐を広げず、次の6インターフェースへ閉じ込める。 ViewModelからは共通の契約だけを参照し、起動時にプラットフォーム別実装を注入する。

境界モバイルSteam
IRewardService既存広告処理へ委譲導線ごとの報酬・解禁条件
IStoreServiceUnity IAPSteam DLC / 所有権
ICloudSaveBackendFirestore RESTFirestore REST + Steam Cloud APIへの自動複製
IAuthServiceGoogle / AppleGoogle / Apple / Steam（各認証は独立）
IAchievementServiceNo-OpSteamworks実績
IReviewPrompt既存レビュー導線No-Op

変更しないもの

ドメインルール、既存モバイルの動作、セーブ互換性を正本とする。 Steam都合の処理をModelへ直接持ち込まず、ViewModel → Root → Repository の流れを維持する。

守る境界

  • #ifは起動・構成・ネイティブSDK境界に限定する。
  • ViewはViewModelとの接続だけを担い、Modelを直接参照しない。
  • UpgradeDomainのC#を変更したら、必ずビルド済みDLLをUnityへ反映する。
  • 広告SDKのネイティブ部分はSteamビルドから除外し、それ以外は必要に応じて無効化する。

3. 領域別の方針と作業

実装は次の6領域に分ける。表の「次に行うこと」はフェーズ2の指示書へそのまま展開する。

領域決定した方針次に行うこと
セーブとサーバー
  • AES暗号化を有効化
  • 平文セーブからの移行を必須化
  • Firestoreをクラウドセーブの正本とする
  • Steam版は確定セーブをSteam Cloud APIへ自動複製する
  • Apple / Google / Steam認証は連携・セーブ統合を行わない
  • FirestoreとSteam Cloudが食い違った場合はユーザーが選択する
  • NetherCompanionはFirestore RESTを継続
 既存CloudSaveを流用し、Steam認証、Steam Cloud複製、競合時の復旧処理を追加する。
マネタイズ
  • 本線はデイリーダイヤ付与型DLC
  • 未受領分は失効させない
  • RemoveAds効果を4分類
  • 不成立時は買い切り化
 DLC所有権、付与履歴、二重付与防止、プランB切替値を設計する。
横長UI
  • 器はVertical / Horizontalで分離
  • 表示部品は共有
  • V/Hのname集合を自動検証
  • リサイズ追従まで対応
 代表画面を1つ選び、横長UXMLとリサイズ追従を試作する。
PC操作
  • Shift+クリックで即時移動
  • ダブルクリックで連続マージ
  • 右クリックで詳細
  • Ctrl+クリックで複数選択
 入力競合と誤操作条件を整理し、連続マージAPIをDomainへ置く。
Steam機能
  • 実績30〜60件、判定はDomain
  • Rich PresenceはCave名 + 深度
  • Overlay中も進行を継続
  • Leaderboardは初回後
 Steamworks.NET初期化、実績ID、翻訳キー、同期タイミングを定義する。
配信とQA
  • ビルドアップロードは手動
  • ストアは7言語
  • ゲーム内13言語を維持
  • Windows / macOSを同時確認
 解像度、DPI、リサイズ、オフライン、長時間放置、公証をチェックリスト化する。
残存リスク: AESのみではメモリ改変と時計改ざんを防げない。現時点では既知の残存リスクとして扱い、 セーブ移行と進行互換性を優先する。

フェーズ2では、決定事項を実装担当者または実装AIが迷わず着手できる単位へ変換する。 指示書は設計の再議論ではなく、変更範囲・依存関係・完了条件を固定するために作る。

すべての指示書に含める項目

  • 目的と根拠となる決定事項
  • 触ってよいファイル、触ってはいけないファイル
  • Model / ViewModel / Viewそれぞれの責務
  • 前提作業と依存関係
  • 受け入れ条件とテスト方法
  • UpgradeDomainのビルドとDLL反映のタイミング
  • 失敗時のロールバック条件

指示書一覧

領域ごとに1本ずつ、計8本をサブページとして用意する。各ページは章ごとにコメントを追加・編集できる。 内容への指摘はページ側へ書き、この本文は決定が変わったときだけ直す。

5. 実装順序

依存関係が強い順に、次の流れで進める。

  1. Standalone検証ビルドを通す既存DLLと主要機能がWindows / macOS向けビルドで動くか確認する。
  2. AppID取得を並行して開始するSteam Direct、審査、ストア準備を実装の待ち時間に進める。
  3. Steamworks.NETとDefineを整理する初期化、失敗時のフォールバック、ネイティブSDK境界を確定する。
  4. PC基本設定とプラットフォーム境界を作る解像度・終了処理・6インターフェースを先に整える。
  5. セーブ、報酬、Steam機能を実装する移行リスクが高い領域から小さなPRで統合する。
  6. 横長UIとPC操作を段階展開する代表画面で成立性を確認後、全画面へ広げる。
  7. 商品、macOS、ストア、QAを仕上げるDLC・公証・多言語・長時間動作を含めてリリース品質へ持っていく。

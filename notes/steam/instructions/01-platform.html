1. 目的

Steam 版で置き換わるのは、広告・課金・クラウドセーブ・ログイン・実績・レビュー誘導の6つだけである。 それ以外はモバイルとまったく同じコードで動く。

にもかかわらず、この6つは呼び出し側に散らばっている。このまま Steam 実装を書き始めると、 プラットフォーム分岐が呼び出し側へ伝染し、そのたびにモバイル版のビルドが壊れる余地が増える。 それを起こさないための土台を先に置くのが、この指示書の目的である。

抽象化そのものが目的ではない。「Steam の実装を足してもモバイルが揺れない」状態が目的であり、 そこへ最も安く到達する形を選んでよい。

2. 方針

優先順位

判断に迷ったときは、上から順に優先する。

  1. モバイル版の挙動を変えないこと。ここだけは譲らない。バイトレベルで同じ経路を通るなら、それが最善
  2. Editor で開発を続けられること。途中の状態でゲームが起動しなくなる作り方をしない
  3. 設計の綺麗さ。最後。境界が多少不格好でも、1・2を満たすなら通す
速度より安全を取る。 この指示書に締切は設定しない。Steam 版が遅れるコストより、 既存プレイヤーの動作を壊すコストの方がはるかに高い。

やり方の方針

  • 既存のクラスを書き換えず、被せる。モバイル実装は既存へ委譲するだけの薄い層でよい。 「既存を整理してから抽象化する」という順序は取らない
  • 迷ったら抽象度を上げない。将来使うかもしれないメソッドを足さない。 いま呼ばれている操作だけを写す
  • Steam 実装は書かなくてよい。本書の完了時点で中身は空でよい。 器と No-Op があって、モバイルが今までどおり動けば成功である
  • 一度に全部やらない。影響範囲の狭い境界から1つずつ入れ、そのたびにモバイルビルドを通す

#if の扱い

書いてよいのは Installer ／ プラットフォーム固有 SDK を直接触る実装クラスの内部 ／ Editor スクリプト の3箇所のみ。 View / ViewModel / Domain には書かない。

これは美観の話ではない。#if が増えた箇所は、そのプラットフォームでビルドするまで壊れたことに気づけないため、 モバイルの出荷経路にとって危険が増える、という理由である。

3. 譲れない前提と契約

ここに書いたものだけが固定である。書いていないことは決めてよい。

触ってはいけないもの

  • Ads/AdRoot.cs、Shop/IAP/ 配下、Firebase/ 配下 ── 1行も変更しない
  • モバイル版のビルド設定・出荷スクリプト

6つの境界

何を境界にするかは決まっている。型の形・命名・置き場は決まっていない。

境界モバイルSteam
広告・報酬既存の広告処理へ委譲導線ごとの報酬・解禁条件（→ 指示書04）
課金Unity IAPSteam DLC / 所有権
クラウドセーブFirestore RESTFirestore REST + Steam Cloud 複製（→ 指示書03）
ログインGoogle / AppleGoogle / Apple / Steam（各認証は独立）
実績No-OpSteamworks 実績（→ 指示書07）
レビュー誘導既存のレビュー導線No-Op

守るべき契約

次の3点は、守らないと呼び出し側の改修が発生する。それを避けるためだけの制約であり、 形を変えて同じ効果が出せるなら、その形でよい。

実装は示さない。 委譲先の実際のメソッド名・戻り値・例外の扱いは、既存コードを読んで合わせること。 上のシグネチャも、実コードと食い違うなら実コード側が正しい。

4. 委ねること

以下は指定しない。実コードを読み、この抽象化にとって自然な形を選ぶこと。 ここを先回りして細かく決めると、実態に合わない設計を強いることになる。

  • ファイルの置き場、名前空間、型名、メソッド名
  • インターフェースの粒度（本書のシグネチャに足す・削る・分割するのは自由）
  • No-Op 実装の作り方と、Editor でどれを注入するか
  • DI への登録の書き方と、既存の登録処理のどこに差し込むか
  • 6境界のうちどれから着手するか（影響の狭いものから、という方針だけ守る）
資料と実コードが食い違ったら、実コードを正とする。 詳細仕様 と docs/steam-release/02_Platform_Abstraction.md には 現状調査の記述があるが、書かれた時点のスナップショットである。 食い違いを見つけたら、それ自体をコメントに残すこと。

5. 完了の判断と、止まる条件

完了したと言える状態

  • Android と iOS のビルドが通る。これは推測で省略しない。実際に通す
  • 既存の報酬導線・課金・ログイン・レビュー誘導が、今までと同じように動く
  • Steam 実装を1つも書いていない状態で、Editor でゲームが遊べる
  • View / ViewModel / Domain に #if が1つも増えていない
  • AdRoot.cs / Shop/IAP/ / Firebase/ の差分がゼロである

手を止めて相談すること

次に当たったら、回避策を考えるより先に共有する。ここで無理に進めた結果がモバイル版の事故になる。

  • 既存クラスを変更しないと成立しない、と判断したとき
  • あるプラットフォームで型そのものが消えるために、呼び出し側へ #if が伝染するとき
  • 境界を1つ入れただけでモバイルビルドが壊れたとき（原因が分かっていても、まず共有する）

戻し方

本書の作業は原則すべて新規ファイルの追加であり、既存ファイルへの変更は呼び出し側の型の差し替えに限られる。 境界ごとに分けて入れておけば、問題が出た境界だけを戻せる。まとめて1回で入れないこと。

1. 目的

Steam 版で置き換わるのは6つだけで、残りはモバイルと同じコードで動く。 その6つが呼び出し側に散らばっているため、このまま Steam 実装を書くと 分岐が呼び出し側へ伝染し、モバイル版のビルドが壊れる余地が増える。

目的は抽象化ではなく、Steam の実装を足してもモバイルが揺れない状態である。 そこへ最も安く到達する形を選んでよい。

2. 方針

優先順位

迷ったら上から優先する。

  1. モバイル版の挙動を変えない。同じ経路を通るなら、それが最善
  2. Editor で開発を続けられる。途中の状態でゲームが起動しなくなる作り方をしない
  3. 設計の綺麗さ。1・2を満たすなら、境界が不格好でも通す
速度より安全を取る。 締切は設定しない。Steam 版が遅れるコストより、既存プレイヤーの動作を壊すコストの方が高い。

やり方

  • 既存クラスを書き換えず、被せる。モバイル実装は既存へ委譲するだけの薄い層でよい
  • 将来使うかもしれないメソッドを足さない。いま呼ばれている操作だけを写す
  • Steam 実装の中身は空でよい。器と No-Op があってモバイルが動けば完了
  • 影響範囲の狭い境界から1つずつ入れ、そのたびにモバイルビルドを通す

#if の置き場

Installer ／ プラットフォーム固有 SDK を直接触る実装クラスの内部 ／ Editor スクリプト の3箇所のみ。 View / ViewModel / Domain には書かない。

#if を書いた箇所は、そのプラットフォームでビルドするまで壊れたことに気づけない。

3. 譲れない前提と契約

固定はここだけ。書いていないことは決めてよい。

触ってはいけないもの

  • Ads/AdRoot.cs、Shop/IAP/ 配下、Firebase/ 配下 ── 1行も変更しない
  • モバイル版のビルド設定・出荷スクリプト

6つの境界

何を境界にするかは固定。型の形・命名・置き場は自由。

境界モバイルSteam
広告・報酬既存の広告処理へ委譲導線ごとの報酬・解禁条件（→ 指示書04）
課金Unity IAPSteam DLC / 所有権
クラウドセーブFirestore RESTFirestore REST + Steam Cloud 複製（→ 指示書03）
ログインGoogle / AppleGoogle / Apple / Steam（各認証は独立）
実績No-OpSteamworks 実績（→ 指示書07）
レビュー誘導既存のレビュー導線No-Op

守る契約

破ると呼び出し側の改修が発生する。同じ効果が出せるなら、形は変えてよい。

委譲先の実際のメソッド名・戻り値・例外の扱いは、既存コードを読んで合わせる。 上のシグネチャが実コードと食い違うなら、実コード側が正しい。

4. 委ねること

以下は指定しない。実コードを読んで決める。

  • ファイルの置き場、名前空間、型名、メソッド名
  • インターフェースの粒度（契約のシグネチャに足す・削る・分割するのは自由）
  • No-Op 実装の作り方と、Editor でどれを注入するか
  • DI への登録の書き方と、既存の登録処理のどこへ差し込むか
  • 6境界のうちどれから着手するか
詳細仕様 と docs/steam-release/02_Platform_Abstraction.md の現状調査は、 書かれた時点のスナップショットである。食い違いを見つけたらコメントに残す。

5. 完了の判断と、止まる条件

完了

  • Android と iOS のビルドが通る。推測で省略せず、実際に通す
  • 既存の報酬導線・課金・ログイン・レビュー誘導が今までと同じように動く
  • Steam 実装を1つも書いていない状態で、Editor でゲームが遊べる
  • View / ViewModel / Domain に #if が増えていない
  • AdRoot.cs / Shop/IAP/ / Firebase/ の差分がゼロ

手を止めて相談する

  • 既存クラスを変更しないと成立しない、と判断したとき
  • あるプラットフォームで型そのものが消えるために、呼び出し側へ #if が伝染するとき
  • 境界を1つ入れただけでモバイルビルドが壊れたとき（原因が分かっていても共有する）

戻し方

境界ごとに分けて入れる。まとめて1回で入れない。問題が出た境界だけを戻せる状態を保つ。

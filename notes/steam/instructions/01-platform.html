1. 目的と根拠

Steam版はモバイル版と同一コードベースで並行運用する。 呼び出し側に #if を足していくと、以降の全作業がプラットフォーム分岐の管理コストに飲まれる。 差分をインターフェースの裏へ隠し、DI登録時に1箇所だけ分岐させる。

3. 実装（スクリプト）

3.1 配置

Assets/1.Games/IdleGem/Platform/ を新規作成する。 Assets/1.Games/IdleGem/ 配下にasmdefは存在せず、すべて Assembly-CSharp に属する。 アセンブリ境界を新設せず、既存の名前空間（IdleSystem_IAP の AdId など）をそのまま参照してよい。

3.2 インターフェース定義

既存メソッドのシグネチャに合わせる。新しい戻り値型を発明しない。 Fin<T> / Unit は IdleSystem.LanguageExt（DLL提供）のもので、AdRoot.cs と同一である。

未確定: Steam版の商品は「デイリーダイヤ付与型DLC」であり、Unity IAP の消費型／非消費型と1対1に対応しない。 StoreProduct に付与量や周期を持たせるかは本指示書では決めない。 ここではモバイルの既存APIを損なわない最小形に留め、DLC固有の情報はマネタイズの指示書で追加する。

3.3 モバイル実装（既存クラスへ委譲するだけ）

既存クラスをコンストラクタで受け取り、同じメソッドを呼ぶだけにする。分岐も状態も持たせない。 これにより、モバイル版は従来と同じ AdRoot の同じメソッドを通る。

調査で判明した訂正: Memo/Current_State_Audit.md は「AppleLogin は Windows でクラスごと消える」と記載しているが、 実際の Firebase/AppleLogin.cs は #if が using ブロック・フィールド・メソッド本体の内側にあり、 クラス自体はWindowsでもコンパイルされる（22行 public class AppleLogin は #if の外）。 したがって MobileAuthService が AppleLogin を参照してもStandaloneでコンパイルは通り、 Windowsでは SignIn() が何もしないだけになる。AvailableProviders はコンパイル対策ではなく UI出し分けのために必要である。

3.4 Steam実装の骨

本指示書ではSteam実装の中身を書かない。クラスの器と #if の位置だけを固定する。 SteamAPI.* の初期化と失敗時フォールバックは指示書02の担当。

Scripting Define の順序に注意。 現状 STEAMWORKS_NET は Android / iPhone にも付いている（ProjectSettings.asset:1051）。 using Steamworks; を書いたファイルを追加した瞬間にモバイルビルドが壊れる可能性がある。 上記の Steam/ 配下のファイルは、指示書02でDefine整理が終わるまでコミットしない。 本指示書のPR範囲では Steam/ ディレクトリは空でよい。

3.5 No-Op（Null）実装

Editorでは Steam クライアントも AdMob も動かない。No-Opをbindしておかないと、Editorで全く遊べなくなる。 報酬は即時付与、購入は成功を返すフェイク、実績は Debug.Log にする。

3.6 DI登録（唯一の分岐）

PlatformInstaller がプロジェクト全体で唯一のプラットフォーム分岐になる。 RootInstaller.cs は既存のbindを保ったまま、この呼び出しを1行追加するだけにする。

Editorでモバイル実装を確認したい場合。 上の分岐は Editor を常に No-Op にする。AdRoot は Editor でテスト用AdUnitIdを持つ（AdRoot.cs:51-52）ため、 Editorで実広告経路を試したい要求は残る。切り替えは #if ではなく EditorPlatformInstaller 内の EditorPrefs フラグで行い、分岐を1ファイルに閉じたままにすること。

3.7 呼び出し側の before / after

報酬ボタンは ReactiveUIElementExtensions.cs の3メソッドを通る。ここの引数型を変えれば、 呼び出し側8ファイル11箇所は本文無改修で済む。

未確定: SettingsLoginHandler のログアウト・アカウント削除は CloudSaveController.DeleteCloudSave() に直接依存している（283行）。 この依存は ICloudSaveBackend の対象ではなく、指示書03で扱う。本指示書では触らない。

4. 作業手順

1項目=1PR。依存順に並べてある。各PRの単位で、モバイル向けビルドが通ることを確認してから次へ進む。

  1. インターフェースと型だけを追加するPlatform/I*.cs と PlatformTypes.cs を新規作成する。この時点でどのクラスからも参照されないため、既存の挙動は一切変わらない。
  2. No-Op実装とEditor用Installerを追加するPlatform/Null/ 一式と EditorPlatformInstaller / PlatformInstaller を作り、RootInstaller.cs へ PlatformInstaller.Install(Container) を1行追加する。Editorで起動して例外が出ないことを確認する。
  3. MobileRewardServiceを追加し、モバイル分岐をbindするMobilePlatformInstaller を追加する。既存の AdRoot bindは残したまま、IRewardService のbindを増やすだけにする。
  4. 報酬ボタン3メソッドの引数型を差し替えるReactiveUIElementExtensions.cs の3メソッドを IRewardService 受け取りに変え、呼び出し側8ファイルの注入型名を機械的に置換する。実機で報酬導線11箇所を通す。
  5. MobileStoreServiceを追加し、ShopViewの#ifを外すRestoreボタンの表示判定を SupportsRestore に置き換える。購入経路そのものは AndroidIAPManagerMono のまま変えない。
  6. MobileAuthServiceを追加し、ログインUIを出し分けるSettingsLoginHandler の GoogleLogin / AppleLogin 直接依存を IAuthService へ寄せる。iOS実機でAppleログインが従来通り動くことを確認する。
  7. IReviewPromptとIAchievementServiceを配線するレビュー導線をラッパー経由に変え、実績はNo-Opをbindしたままにする。ゲームロジックから分岐なしで Unlock() を呼べる状態にする。
  8. Steam実装の器だけを用意するSteamPlatformInstaller の空実装を置く。Steam/ 配下の using Steamworks; を含むファイルは、指示書02でScripting Defineの整理が終わるまでコミットしない。

モバイルビルドが壊れていないことの確認（必須）

この確認を通さずにマージしない。実ユーザーがプレイ中のモバイル版を守るための唯一の関門である。

  1. Android実機ビルドが成功する。 Assets/Editor/AndroidBuildScript.cs の経路でビルドし、エラー0で完了する。
  2. iOS実機ビルドが成功する。 Xcodeプロジェクト出力まで通り、PostBuildStep.cs がエラーを出さない。
  3. 報酬導線11箇所すべてで、従来どおり動画広告が再生され報酬が入る。 オフラインボーナス×2 / プレステージSoil / プレステージTear / ランダムタイムブースト / バトル戦利品×2 / 固定ブースター受取 / CaveATK / BattleATK / TimeATK / デイリーダイヤ / デイリー箱。
  4. 広告削除購入済みアカウントで、従来どおり広告なしの即時付与になる。 AdRoot.IsRemoveAdsPurchased 経路が生きていること（AdsClient は無改修なので値の供給元は変わらない）。
  5. Shop画面で購入が完走する。 ダイヤ商品1件をサンドボックスで購入し、付与とレシート処理が従来どおり行われる。
  6. iOSでRestoreボタンが表示され、復元が成功する。 MobileStoreService.SupportsRestore == true による表示であること。
  7. Google / Appleログインが従来どおり成功し、クラウドセーブ画面が開く。 ログイン後にユーザー名ラベルが表示される。
  8. Androidでレビュー誘導が従来どおりPlayストアを開く。 MobileReviewPrompt 経由で OpenReviewPage() が呼ばれる。
Standaloneビルドは本指示書の受け入れ条件に含めない。 IdleSystem.*.dll 群がStandaloneで動作するかは未検証であり、その検証は指示書02が担当する。 本指示書では「Steam実装の器が用意されている」ことまでを条件とする。

6. ロールバック

本指示書の作業は、モバイル版の報酬・課金・ログインという収益と進行の中枢に触れる。 少しでも既存挙動の差異が疑われたら、原因究明より先に戻す。

差し戻す条件

状態判断
即時Android / iOSのビルドが通らない
即時報酬導線11箇所のいずれかで、広告が再生されない・報酬が入らない・二重に入る
即時課金が完走しない、または購入済み権利（remove_ads / idle_gem_booster_plus / idle_gem_nether_plus）が失われる

戻し方

  1. PR単位でrevertする作業手順1〜8は依存順に並べてあるため、後ろのPRから順にrevertすれば中間状態でも整合する。
  2. 最後に戻すのは RootInstaller.cs の1行PlatformInstaller.Install(Container) を消せば、既存のbindだけが残り、抽象化導入前と同じ構成に戻る。
  3. DLL再ビルドは不要本指示書はUnity側のみを変更しているため、Assets/Plugins/*.dll は元のままでよい。
退避条件: モバイル版のストア申請・アップデート提出が予定されている期間は、手順4以降（呼び出し側の型置換）をマージしない。 インターフェース定義とNo-Op（手順1〜2）までは既存挙動に影響しないため、いつでもマージしてよい。

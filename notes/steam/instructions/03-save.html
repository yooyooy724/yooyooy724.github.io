1. 目的

Steam 版で必要になるのは、PC をまたいだ復元とローカルファイルの改ざん耐性の2つ。 モバイル版は平文セーブのまま実ユーザーが遊んでおり、Steam 版だけの都合で形式を割ると 両版の互換が切れる。だから移行は両版共通の作業になる。

クラウドの正本は Firestore のまま変えない。Steam Cloud は複製先であり、 Steam の流儀（別 PC で自動復元）を成立させるためだけに使う。

改ざん耐性には到達点がある。どこまでを守り、どこから先を諦めるかを次章で固定する。

2. 暗号化で守るもの、守らないもの

目的は「カジュアルな改ざんの抑止」まで。 鍵は実行ファイルへ埋め込む以上、取り出せる。ファイルの改ざんそのものは防げない。 防げるのは「メモ帳で開いて数字を書き換える」ところまでで、そこで止まらない相手には効かない。 「一切できないようにする」は原理的に不可能であり、目標に置かない。

鍵

  • 全ユーザー共通の固定ランダム値を1つ埋め込む
  • 端末ごとの鍵は採らない。鍵を失えばセーブが全損する経路を新しく作ることになり、 守れる範囲の広がりに見合わない
  • 改ざん検知（HMAC 等）は足さない。鍵が取り出せる以上、署名も同じ鍵で作り直せる。 手間だけ増えて抑止力が変わらない

暗号化する範囲 ── ローカル3経路すべて

  • local_save … 通常のセーブ。BindRepository が組み立てる経路
  • manual_backup … アプリ内の復元ポイント
  • cloud_save … クラウドとやり取りするローカルの受け皿

1つでも平文で残ると抜け道になる。3経路のどれか1つから読めれば、 そこで書き換えて本体へ戻せてしまう。3つまとめて切り替える。

クラウドへ載せる中身は平文 JSON のまま

  • 暗号化はローカルのファイルにだけ効かせる。Firestore に載るのは復号済みの平文 JSON
  • クラウド側まで暗号化すると、既存のクラウド経路・Firestore に入っているデータ・ NetherCompanion がまとめて壊れる。そこまで広げない
  • 暗号化はファイルの読み書きの境目だけで行い、その外側は今までどおり平文 JSON を扱う

既存の暗号化実装は使わない

EncryptedUpdateJsonPlayerData.cs と AES.cs は実装済みだが一度も使われていない。 これらはアトミック書き込み・変更検知・失敗時の復旧を持たないため、 BindRepository のフラグを立てて有効化すると、 いま平文側が持っている安全装置を失う。この実装は捨てる。

代わりにドメイン側にバイト列変換の口を1つ作り、既存の保存経路はその口を通すだけにする。 暗号化するかどうかも、何で暗号化するかも、その口の内側へ閉じる。

口の形（型名・粒度・置き場所）は実コードを読んで決めてよい。 保存経路の組み立ては RepositoryRegister.cs の BindRepository から辿れる。 資料と実コードが食い違ったら実コードが正。

3. 方針

優先順位

  1. 既存プレイヤーのセーブを壊さない。絶対条件。疑わしい変更は入れない
  2. 復旧できること。失敗したときに元へ戻せない処理を作らない
  3. 改ざん対策の強さ。最後。AES で防げない攻撃（メモリ改変・時計改ざん）は 受け入れた残存リスクであり、対策をこれ以上広げない

着手順

  1. 二重起動の防止。PC では同じセーブを2プロセスが書ける。破損原因の筆頭を先に塞ぐ。指示書01 を待たずに着手できる
  2. 平文 → 暗号化の移行（3経路まとめて）
  3. Steam Cloud への複製と競合処理

二重起動

  • 2つ目のプロセスは起動しない。気づいた時点で、セーブに触れる前に終了する
  • すでに動いている側を前面に出す処理は作らない。OS ごとのウィンドウ操作が要る割に、 得られるのは体裁だけ
  • Steam の多重起動防止に任せない。あれは Steam クライアント経由の起動にしか効かず、 exe を直接叩かれると素通りする。ガードはゲーム側に置く
  • 現状は forceSingleInstance: 0。PC ではライブラリ・ショートカット・再起動で容易に起きる

移行の原則

  • 読みは両対応、書きは暗号化。平文が読めなくなる瞬間を作らない
  • 切り替えは1リリースで行う。読みの両対応と書きの暗号化を同じリリースへ入れる。 「先に読みだけ対応した版を配り、次のリリースで書きを変える」2段階は採らない。 平文が残るので、旧版が起動しても読めなくなることはない
  • 移行後も平文を永久に残す。消さない。移行が想定外に失敗したとき、手で戻せる余地を残しておく
  • ただし移行済みフラグが立った後は、平文へフォールバックしない。 「暗号化ファイルが読めなければ平文を読む」という作りにすると、 暗号化ファイルを消すだけで平文が使われる抜け道ができる。 フラグ以降は、暗号化ファイルが読めない状態を異常として扱う
  • 移行は起動時に自動で行い、プレイヤーに操作を求めない

クラウドの構成

  • Firestore が正本。Steam 版もモバイル版と同じ経路で Firestore へ保存する
  • クラウドへ載せる中身は平文 JSON のまま。暗号化はローカルのファイルにだけ効かせる（2章）
  • Steam Cloud へは確定したセーブを複製するだけ。復元の第一候補は常に Firestore
  • Apple / Google / Steam の認証は独立させ、アカウント連携・セーブ統合を作らない
  • Firestore と Steam Cloud が食い違ったら、どちらを採るかはプレイヤーに選ばせる。 自動でどちらかを捨てない
  • NetherCompanion は Firestore REST のまま変えない

クラウドセーブの境界（指示書01）越しに実装する。 既存の CloudSave 実装は流用し、Steam 向けの複製と競合処理だけを足す。 資料と実コードが食い違ったら実コードが正。食い違いはコメントに残す。

4. あなたにお願いすること

次の確認は自動テストで代替できない。実施した結果をそのまま貼ってほしい。

#やること確かめること
1実際の平文セーブ（あなたの手元のプレイデータのコピー）で移行を走らせる進行が1項目も欠けずに引き継がれる
2PC を2台（または2環境）用意し、片方で進めてもう片方で起動するSteam Cloud 経由で復元される
3両方をオフラインで進めてから接続し、競合を起こす選択画面が出て、選んだ側が残る
4オフラインのまま起動 → プレイ → 終了 → 再起動するローカルだけで完結し、何も失われない
5ゲームを二重起動する2つ目が起動しない（前面化もしない）
6移行が済んだ後、暗号化ファイルを手で消してから起動する平文へ戻らず、異常として扱われる
1 は必ずコピーで行い、原本を残してください。 移行テストに使ったデータは、失敗した場合そのまま破損サンプルとして貼ってもらいます。

5. 完了の判断と、止まる条件

完了

  • 上の手動テスト6件がすべて通っている
  • 平文セーブの端末を更新しても、今までどおり遊べる（モバイル両OSで確認）
  • ローカル3経路（local_save / manual_backup / cloud_save）の ファイルが、いずれも平文で読めない
  • Firestore 側のデータは今までと同じ平文 JSONで、NetherCompanion が動いている
  • 移行後も平文ファイルが残っている
  • ドメインの変更分に単体テストがあり、通っている

手を止めて相談する

  • 移行ロジックが1件でもデータを落とすケースを見つけたとき
  • セーブデータの形式・スキーマ自体を変えないと成立しない、と判断したとき
  • Steam Cloud の容量・ファイル数制限に既存セーブが収まらないとき
  • 競合の選択画面で「どちらを選んでも何かが失われる」ケースが出たとき
  • 3経路のうち、どれか1つだけ暗号化できない事情が出たとき（1つでも平文なら抜け道になる）

戻し方

暗号化の書き込みはフラグで無効化できる形にしておき、問題が出たら書き込みだけを平文へ戻す。 読みの両対応は残り、平文も消していないので、どの時点のセーブも読める状態が保たれる。

これは自動フォールバックとは別物。 ここでいう戻しはこちらが明示的にフラグを倒す運用操作である。 「暗号化ファイルが読めなかったら平文を読む」という実行時の自動切り替えは作らない。 自動にすると、ファイルを1つ消すだけで平文経路へ落とせてしまう。

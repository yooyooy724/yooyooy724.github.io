横長レイアウト

縦画面 UI を横長で成立させる。器を Vertical / Horizontal で分け、表示部品を共有する。

最終更新: 2026-08-06　／　担当: Unity View（UXML / USS / View）

成否の基準 代表画面1つが横長で成立し、同じ作り方を残りの画面へ機械的に適用できると確認できている。

1. 目的

全 UI が縦画面前提で作られており、横長対応は移植の中で最大工数の領域になる。 だから最初にやるのは全画面の変換ではなく、作り方を1画面で確立することである。 ここで確立した型がそのまま残りの画面の仕様になる。

方針は「縦のUIを横に並べ直す」ではなく「展開する」。 縦画面で階層に隠れていたもの（タブの奥、スクロールの先）を、横幅を使って同時に見せる。

2. 方針

優先順位

  1. モバイルの縦画面を変えない。縦向けの UXML・USS への変更はゼロが原則
  2. 型の再現性。2画面目以降が「同じ手順の繰り返し」になること。画面ごとの一点物にしない
  3. 横長での見栄え。成立が先、磨きは後

器と部品

  • 器（画面の骨格）だけを Vertical / Horizontal の2枚に分ける。表示部品は1つを共有する
  • View（C#）は1つのまま。器がどちらでも同じ name で部品を引けることが共有の条件
  • V/H の name 集合の一致は自動検証する。片方に無い name は実行時まで発覚しないため、 Editor テストで先に落とす。これが型の安全装置であり、省略しない
  • V/H の判定はアスペクト比。プラットフォームでは判定しない（#if を書かない）
  • リサイズ追従まで対応する。PC はウィンドウ幅が動的に変わる。起動時判定だけで済ませない

ナビゲーション

  • 横長では下タブバーをやめ、右レールへ移す
  • 画面ごとの展開のしかた（何を同時に見せるか）は、縦版の階層を読んで決めてよい。 決めたことは型として記録し、後続画面の判断材料にする

進め方

  • 代表画面を1つ選び、型が通しで成立してから広げる。全画面を並行で始めない
  • 代表画面は「タブ・リスト・詳細の階層が深く、他の画面の代表になれるもの」から選ぶ。選定理由を残す
  • 1.0 でどこまで磨くかの線引きは、代表画面が成立した後にあなたへ相談する

3. 完了の判断と、止まる条件

完了

  • 代表画面が横長（16:9 前後）で成立し、ウィンドウをドラッグでリサイズしても崩れず V/H が切り替わる
  • V/H の name 集合検証が Editor テストとして存在し、意図的に name を消すと落ちる
  • 縦画面の表示がビフォーアフターで一致している（モバイル解像度で目視）
  • 2画面目の作業手順が「Vertical をコピーして展開を決め、検証を通す」だけになっている

手を止めて相談する

  • 部品共有のために縦版の UXML に手を入れる必要が出たとき（原則違反。やる前に相談）
  • 代表画面で型が成立せず、画面ごとの一点物になりそうなとき
  • リサイズ追従の負荷（再構築コスト）が目に見えて重いとき

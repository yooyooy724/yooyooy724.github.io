1. 目的

タッチ前提の操作（タップ・長押し・ドラッグ）は PC でもそのまま動くが、 マウスとキーボードにしかない入力（修飾キー・右クリック・ダブルクリック・ホバー）が遊んでいる。 PC で速く快適に操作できることが目的であり、新しい操作を覚えないと遊べない状態にはしない。 既存操作だけでも今までどおり遊べることを保つ。

2. 方針

優先順位

  1. タッチの挙動を変えない。追加はすべて「マウス・キーボードがあるときだけ増える操作」
  2. 誤操作で資産が動かないこと。特に一括系（連続マージ）は、意図しない発火が実害になる
  3. 操作の速さ・快適さ

追加する操作

入力効果
Shift + クリック即時移動（ドラッグの省略）
ダブルクリック連続マージ
右クリック詳細表示
Ctrl + クリック複数選択
数字キー画面切り替え
  • 各操作について、競合しうる既存操作（長押し・ドラッグ・シングルタップ）との切り分けを先に決めてから実装する
  • 入力の有無はランタイム判定。#if で分岐しない（既存の入力処理がすでにこの形）
  • QWERT へのショートカット割当は 1.0 では見送り。ただし数字キーのディスパッチャは 後からキーを足せる形にしておく

連続マージはドメインに置く

  • 「打ち止めまでマージする」という操作はゲームのルールであり、View の都合ではない。 1回の呼び出しで完結する API をドメインに置き、View はそれを1回呼ぶだけにする
  • View 側でマージを繰り返すループを書かない。途中で画面が閉じられたときに中途半端に終わる実装を禁じる
  • ドメイン API は単体テストで検証できる。何がどこまでマージされるかのルールはテストで固定する
  • ドメイン API を先に作り、テストを通してから View の入力を繋ぐ

既存の入力処理・Equipment の操作実装は実コードから拾う。資料と食い違ったら実コードが正。 食い違いはコメントに残す。

3. 完了の判断と、止まる条件

完了

  • 連続マージのドメイン API に単体テストがあり、マージ順・打ち止め条件・結果の内容が固定されている
  • 追加した5操作が PC（Editor または Standalone）で動く
  • マウスを使わずタッチ相当の操作だけでも、今までどおりすべて操作できる
  • モバイル実機でタッチ操作の回帰確認が済んでいる（長押し・ドラッグ・タップ）
  • View / ViewModel / Domain に #if が増えていない

手を止めて相談する

  • 追加操作と既存のタッチ操作の競合が、切り分けでは解消できないと分かったとき
  • 連続マージの「打ち止め」ルールに複数の解釈があり得るとき（仕様の決定なのでこちらで決めない）
  • 既存の入力処理の構造が、修飾キーの追加に耐えない形だったとき

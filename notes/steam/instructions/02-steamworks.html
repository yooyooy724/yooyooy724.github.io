1. 目的

ゲームロジックはビルド済み DLL として Unity に持ち込まれている。モバイルで動くことは分かっているが、 Standalone で動くかは一度も確かめていない。Standalone はスクリプトバックエンドも API プロファイルもモバイルと違う。

ここが動かない場合、移植計画そのものの見直しになる。 仕様が固まるのを待たず、最初に確かめる。

Steamworks SDK の整理と初期化は従属的な作業である。 Steam を絡めた状態で失敗すると「DLL のせいか Steam のせいか」が分からなくなるため、先に足場を綺麗にする。

2. 方針

切り分けられる順に進める

まとめて進めると、失敗したときに原因を特定できない。

  1. Steam を一切絡めない状態で Standalone ビルドを通す。ここで DLL の可否が分かる
  2. Steamworks SDK の重複を解消する
  3. Scripting Define を整理する
  4. 初期化処理を入れ、Steam を絡めた状態でもう一度確かめる

1 で結論が出た時点で、主目的は達成である。

慎重さの配分

対象慎重さ理由
検証用のシーン・スクリプト・ビルド設定低い使い捨てでよい。汚くても速く答えが出る方が価値がある
Steamworks SDK の重複解消中どれが効いているか不明なまま消すと、原因が分からなくなる
Scripting Define の変更高いモバイルの出荷経路に直結する

検証コードの品質を上げることに時間を使わない。残す価値があるのは再実行できる仕組みだけである。

Define を変えたら、その場で Android と iOS のビルドを通す。 後でまとめて確認しない。壊れたことに気づくのが出荷直前になる。

Steam が無い環境を壊さない

Steam クライアント未起動・オフライン・Editor 実行は通常の状態である。 初期化が失敗しても、ゲームは何事もなく起動する。

3. 譲れない前提と契約

固定はここだけ。書いていないことは決めてよい。

前提

  • 既存の .cs は編集しない。追加物はすべて新規ファイルでよい
  • 既存のシーン構成・起動経路を変えない。検証は本編の起動経路の外で行う
  • AppID 3217600 は旧作用。本作の AppID はここでは確定させない。検証は Steam 公式のテスト用 AppID で足りる
  • ドメイン（NewCubeUpgradeDomain/）は変更しない

守る契約

破ると後続の全指示書に波及する。

Steamworks 名前空間を、SDK を直接触る1ファイルの外へ出さない。 漏れた分だけ「Steamworks が無い環境でコンパイルできないクラス」が増える。 他のクラスには上の契約だけを見せる。

steam_appid.txt をリリースビルドの成果物に含めない。開発時のみ実行ファイルの隣に置く。

4. 委ねること

以下は指定しない。DLL が動くかを最短で確かめる、という目的に対して有効な形を選ぶ。

  • 検証の方法。シーンを作る、テストランナーを使うなど、確かめられれば何でもよい
  • 結果の見せ方（画面表示／ログ／ファイル出力）。macOS で手元から見られることだけが要件
  • 初期化処理をどのクラスに持たせるか、どこで生成するか、コールバックをどこで回すか
  • AppID の持ち方と、後で差し替えるための置き場
  • SDK のバージョンを固定するかどうか、するならどのバージョンか
詳細仕様 と docs/steam-release/Memo/ にある SDK の重複や Define の記述は、書かれた時点のスナップショットである。 削除・変更の前に現物を確認する。食い違いを見つけたらコメントに残す。

5. 完了の判断と、止まる条件

完了

  • Windows と macOS の両方で、ドメイン DLL がロードできるかの答えが出ている。 動く／動かないのどちらでも、答えが出ていれば主目的は達成
  • Steam クライアント未起動でもゲームが普通に起動する
  • Android と iOS のビルドが通る。Define を触ったなら実測する
  • Steamworks SDK の参照が1系統に絞られている
  • DLL を更新したあと、同じ検証をもう一度回せる
macOS を「たぶん同じ」で済ませない。 Windows で通っても macOS で落ちることがある。独立した関門として扱う。

手を止めて共有する

  • DLL がロードできなかったとき。回避策を試す前に、結果をそのまま共有する
  • 切り分けがドメイン側の変更（ターゲットフレームワークの変更など）に及ぶと分かったとき。 モバイル版が使う DLL も同時に変わる
  • Define を戻してもモバイルビルドが直らないとき

戻し方

Define の変更は単独で戻せる形にしておく。モバイルが壊れたときは、調査より先に戻す。 検証用の追加物は、問題が出なければ残してよい。

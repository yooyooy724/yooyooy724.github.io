この指示書の完了条件 Steamworks.NET の参照が Packages/manifest.json 1箇所に一本化され、STEAMWORKS_NET が Standalone 限定になり、 SteamAPI.Init() の成否によらず起動する SteamManager が動作したうえで、 Windows / macOS の Standalone 検証ビルドが起動し、ドメイン DLL のロード結果が画面とログに出ている。

1. 目的と根拠

この指示書の主目的は Standalone 検証ビルドを通すことである。 Steamworks.NET の整理と SteamManager の作成は、その検証を意味あるものにするための前準備として同じ指示書に入れている。

親ページの決定この指示書での扱い
Standalone検証ビルドを最初に通す本書の主目的。最小シーン + 反射によるアセンブリロード確認で、DLL の可否を最速で判定する。
Steamworks.NETとDefineを整理するAssets 側の残骸2つを削除し Packages/manifest.json へ一本化。STEAMWORKS_NET を Standalone 限定にする。
初期化、失敗時のフォールバックを確定するSteamManager を新規作成。SteamAPI.Init() が false でも起動を止めない。
#if は起動・構成・ネイティブSDK境界に限定する#if を書く場所を Installer ／ Steam 固有実装クラス内部 ／ Editor スクリプト の3箇所に限定する。ViewModel・Domain には書かない。
モバイル版を壊さない既存の .cs は1ファイルも編集しない。追加のみ。Define も Android / iPhone から STEAMWORKS_NET を抜くだけで、モバイルの挙動は変わらない。
AppID 3217600 は旧作用。新規取得本書では AppID を確定させない。検証は Spacewar（480）で行い、実 AppID は取得後に差し替える。

なぜ検証ビルドを最優先に置くか

本プロジェクトのゲームロジックは Assets/Plugins/*.dll としてビルド済みで持ち込まれており、 これが Standalone で動くかは一度も検証されていない。 ここが動かない場合、影響は指示書02の範囲では収まらず、移植計画そのものの見直しになる。

未確認: 固定すべきタグ名（上の 20.2.0 はプレースホルダ）。 Packages/packages-lock.json に現在解決されているコミットハッシュが記録されているので、 まずそれを読んで「今どのバージョンが入っているか」を確定させてからタグを決めること。 現在動いているものと違うバージョンへ不用意に上げない。

3.3 SteamManager を新規作成する

SteamManager は本リポジトリに存在しない。Steamworks.NET が同梱しているサンプル実装も、 パッケージ参照では Assets/ 下に展開されないため、自前で持つ。

このクラスは「プラットフォーム固有 SDK を直接触る実装クラス」であり、#if を書いてよい3箇所のうちの1つにあたる。 Steamworks 名前空間がこのファイルの外へ漏れないことが設計上の要件である。

Editor での扱い: UNITY_EDITOR でも UNITY_STANDALONE は真になるため、 Editor 実行時も SteamAPI.Init() が呼ばれる。steam_appid.txt がプロジェクトルートにあり Steam クライアントが起動していれば成功し、無ければ false になって No-Op へ落ちる。 どちらでも Editor で遊べる状態は壊れない。 RestartAppIfNecessary だけは !UNITY_EDITOR で囲ってあり、Editor が勝手に終了することはない。

3.4 IsInitialized を他クラスへ渡す

SteamManager.IsInitialized を各所から直接 static 参照させない。 参照が増えるほど「Steamworks が無い環境ではコンパイルが通らないクラス」が増えていくためである。 インターフェース1枚を挟み、bind 時に1回だけ分岐する。

RootInstaller.cs からの呼び出しは本書では行わない。 PlatformInstaller.Install(Container) の1行追加は指示書01の受け入れ条件に含める。 本書のゴールは「検証ビルドが通ること」であり、既存の起動経路に手を入れると 失敗したときの原因が Steam なのか DI なのか切り分けられなくなる。

3.5 検証ビルド用の最小シーンスクリプト

これがこの指示書の核心。ゲーム本体を起動せず、 Assets/Plugins/ の各アセンブリを反射でロードして結果を画面とログに出す。 ゲームロジックを一切呼ばないことで、「DLL がロードできない」と「ゲームのバグ」を確実に切り分ける。

シーン Assets/1.Games/IdleGem/Platform/Verify/StandaloneVerify.unity は、 空の GameObject 1つに StandaloneSmokeTest を付けただけにする。 カメラも Light も Zenject の SceneContext も置かない。

ログの場所（検証時に必ず見る）: Windows は %USERPROFILE%\AppData\LocalLow\IdleSystem\<productName>\Player.log、 macOS は ~/Library/Logs/IdleSystem/<productName>/Player.log。 <productName> は ProjectSettings.asset の productName に一致する。 画面表示（IMGUI）が出ない場合でも、ログ側に [SmokeTest] が残っていれば起動自体は成功している。

4. 作業手順

依存順に並べる。1〜4（検証ビルド）を最優先に置くのは、ここで DLL が動かなければ 5 以降の作業がすべて無駄になるため。 Steamworks の整理を先にやると、失敗したときに「Steam のせいか DLL のせいか」が分からなくなる。 まず Steam を一切絡めない状態で Standalone ビルドを通す。

  1. ドメイン DLL を最新へ揃えるgo run Go/buildblazor/main.go を実行し、Assets/Plugins/ の UpgradeDomain.dll ほか6件を最新にする。古い DLL で検証しても結論にならない。
  2. 検証シーンとスモークテストを追加するStandaloneSmokeTest.cs と StandaloneVerify.unity を作る。既存シーンリストには追加しない。
  3. Windows 検証ビルドを取るBuild/Verify/Windows (x64) を実行し、起動して RESULT: OK を確認する。この時点ではまだ Steam に触れていない。
  4. macOS 検証ビルドを取る同じ手順で StandaloneOSX。System.Windows.Forms.dll が同梱されるため、Windows が通っても macOS で落ちる可能性がある。ここが独立した関門である。
  5. 結果を記録し、NG なら止まるNG のアセンブリ名と例外メッセージをそのまま記録する。ここで NG が出た場合、以降の手順へ進まず 6章のロールバック判断へ移る。
  6. Steamworks.NET を一本化するAssets/Steamworks.NET_15.0.1/ と Assets/com.rlabrecque.steamworks.net/ を .meta ごと削除する。packages-lock.json で現行バージョンを確認してから manifest.json にタグを固定する。
  7. Unity を再起動しコンパイルを確認する削除の反映には再インポートが要る。Steamworks 名前空間が Standalone で解決できることをコンソールで確認する。
  8. Scripting Define を整理するUnity Editor を完全に終了してから ProjectSettings.asset を編集する。または Player Settings 画面から入力する。git diff で scriptingDefineSymbols 以外に差分が無いことを確認する。
  9. Android / iOS ビルドが通ることを確認するDefine を抜いた影響がモバイルへ及んでいないことを、この時点で必ず確かめる。後回しにしない。
  10. SteamManager と ISteamRuntime 一式を追加するPlatform/ 配下に5ファイル。RootInstaller.cs は編集しない。
  11. steam_appid.txt を 480 にして初期化を確認するSteam クライアントを起動した状態で Editor 実行し、[Steam] SteamAPI.Init() succeeded をログで確認する。次に Steam クライアントを終了して、false でもゲームが起動することを確認する。
  12. 検証シーンに SteamManager を通した状態で再度ビルドするSteam.SteamManager.Diagnostics の行が検証画面に出ることを Windows / macOS 両方で確認する。
  13. steam_appid.txt を元に戻す／除外を確認するリリースビルドの成果物に steam_appid.txt が含まれないことを確認する。開発時のみ実行ファイルの隣に置く運用とする。
AppID 取得は並行して進める。 親ページの実装順序 2 に該当し、本書の作業をブロックしない。 検証は Spacewar（480）で完結するため、AppID 待ちを理由に手を止めない。 取得後は SteamManager.AppId、steam_appid.txt、 applicationIdentifier.Standalone（現在 com.idlesystem.IdleSphere）を別PRでまとめて差し替える。

Steamworks 削除後に Standalone のコンパイルが壊れた削除PRを revertAssets/ 側の2ディレクトリは実質空なので、復元しても効果は無いはず。原因は manifest.json 側にある。packages-lock.json を元コミットへ戻す
SteamAPI.Init() の失敗でゲームが起動しない設計違反。SteamManager を修正する（差し戻しではない）例外を catch し切れていない箇所を特定する。「Init が成功する前提」のコードを1行も書かないという契約に戻す
SteamManager がモバイルビルドを壊したPlatform/ 追加PRを revert追加のみのPRなのでファイル削除で戻る。既存ファイルは編集していない

ドメイン DLL が Standalone で動かなかった場合

受け入れ条件 A4 が満たせなかったときは、この指示書を中断し、次の順に切り分ける。 原因の切り分けが終わるまで、指示書01以降には着手しない。

順見直す対象具体的に見るもの
1 Assets/Plugins/*.dll.meta のインポート設定 IdleSystem.*.dll と UpgradeDomain.dll の .meta には PluginImporter ブロックが無い（2行のみ）。Editor の Inspector で Any Platform が有効になっているか、Standalone が除外されていないかを目視する。除外されていたら .meta を BigDouble.dll.meta と同じ形へ揃える
2 Standalone の API 互換レベル ProjectSettings.asset:1081-1083 の apiCompatibilityLevelPerPlatform。Standalone が 3、Android が 6 で不一致。Android と同じ値へ揃えて再ビルドし、結果が変わるか見る
3 重複する BCL アセンブリ Microsoft.Bcl.AsyncInterfaces.dll を Standalone から除外して再ビルドする。API プロファイル側が同じ型を持っている場合、型の重複でロードが失敗しうる
4 macOS 固有の同梱物 macOS のみ NG の場合、System.Windows.Forms.dll（Standalone 全 OS で enabled: 1、自作コードからの参照ゼロ）を除外して再ビルドする。discord-rpc.dll / libdiscord-rpc.dylib も同様に切り離して試す
5 ドメイン側の TargetFramework 1〜4 で解決しない場合のみ。NewCubeUpgradeDomain/*/*.csproj の netstandard2.1 を netstandard2.0 へ落として再ビルドし、DLL を差し替えて検証する。ここまで来た場合はドメイン側の変更になるため、指示書02の範囲を超える。移植計画そのものを再検討すること
5 に到達した場合は作業を止めて共有する。 ドメインのターゲットフレームワークを下げると、モバイル版が使っている DLL も同時に変わる。 リリース済みモバイル版への影響評価なしに実施してはいけない。

戻さないもの

  • 検証ビルド一式（Platform/Verify/ と Assets/Editor/StandaloneVerifyBuild.cs）は残す。DLL を更新するたびに再実行できる形にしておく価値がある。
  • AppID の新規取得手続き。実装の成否と独立して進める。

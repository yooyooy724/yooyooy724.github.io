開発方針（全体）

2026年10月01日10 min read

すべての開発プロジェクトに共通する作り方。前半は過去の意思決定（遡及ADR）から繰り返し現れる原則、後半は開発サイクルの自動化の提案。

設計の原則

原則中身根拠となった決定
ルールを表示から切り離すゲームのルール（ドメイン）を Unity から切り離し、別の画面（モバイル・Web・ECS）につなぎ直せるようにする「ドメインから永続化を外しアセンブリで層を分ける」（2024-02）、「ドメインを別リポジトリに出す」（2025-03）、Blazor での試作（2025-03）
コードを仕様の正本にする実装した後の仕様の正本は、ドメインの C# コードにする「実装後の仕様の正本はドメインの C# コードにする」（2026-07）
正本は1か所同じ情報（設定・翻訳・所持状態）を2か所に持たない。派生するものは毎回作り直す自動化設定の一本化（2026-08）、翻訳の元データの一本化（2026-08）、「所持 Spell は起動のたびに受領記録から作り直す」（2026-08）
既存のセーブを壊さないリリース済みのセーブ互換は、全更新の約束にする。例外として消すときは理由を書いて告知する「既存セーブを壊さないことを全更新の約束にする」（2026-07）、Lint でセーブに関わる変更を禁じた決定（2026-08）
事故は構造で防ぐ不具合を局所で直して終わらせず、同じ事故が構造的に起きない形にする「Challenge の開始は World の切り替えとして扱う」（2026-08）、Tick ループの例外隔離（2026-07）、クラウド上書き事故の対策（2026-07）
推測で最適化しない性能改善は計測から始め、決めたこと・理由・根拠を決定ログに残す「性能改善は計測と決定ログで進める」（2026-08）
境界で吸収する新しいプラットフォーム対応は、ゲームロジックに手を入れず境界のインターフェースで吸収する「PC 対応はゲームロジックに手を入れず境界のインターフェースで吸収する」（2026-07）

AI エージェントとの分担

原則中身根拠となった決定
目的と方針で頼む指示は手順ではなく、目的と方針を短く伝える「AI への指示書は手順ではなく目的と方針で書く」（2026-08）
詰めてから作らせるまず計画させ、設計を問い詰めてから実装に移る。決定を集めた企画ページから指示書を作る「AI にはまず計画させ勝手に編集させない」（2025-11）、「実装前に grill で設計を詰める」（2026-08）、Steam 移植の進め方（2026-07）
隔離して任せる大きな実装は worktree などの隔離した場所で任せる。メインの AI は割り振りとレビューに徹する「AI の大きな実装は worktree で隔離する」（2026-07）、メイン AI の役割の決定（2026-07）
見た目は実物で決める見た目は文章でやり取りせず、実物を見て決める。合わなければ AI に追わせず自分で素材を作る「見た目の調整は AI に追わせず自分で素材を作る」（2026-09）、「見た目が合わないなら擬似表現をやめて本物の3Dにする」（2026-08）
繰り返しは型にする繰り返す作業はスキルにし、失敗も理由つきで書き込む動画加工のスキル化（2026-09）、UI の禁止事項をスキルに残した決定（2026-08）
細部は任せ、方向だけ決める細かいデザイン判断は遊び手の体験を基準に任せ、本人は方向だけ確認する「細かいデザイン判断は本人に聞かず方向だけ確認する」（2026-09）

残し方

  • 読むより見てわかる形で残す（結論が先、表と箇条書き、本文だけ）。
    • 根拠: 報告の形式の決定（2026-08）、保管庫の文章の決定（2026-08）

自動化の原則

  • 人が判断する箇所は「確定にするか」だけに絞る。集める・まとめる・下書きするは機械に任せる
  • 機械が書いたものは必ず 提案 として置き、人の承認なしに確定させない
  • 素材（一次情報）は取得日・集計期間・取得元つきで保存し、書き換えない
  • 判定だけで済む大量の処理は判定専用モデル（Jev）、文章が要る処理は Claude に振り分ける

自動化できる箇所

開発サイクルの流れごとに、自動化できる処理を並べる。

#流れ自動化する処理道具人がやること
1App → 統計（情報圧縮）ストアの数値（DL数・収益・継続率）を定期取得し、素材として保存App Store Connect API／Google Play Console／Steamworks、定期実行（GitHub Actions か Claude の定期ルーティン）なし
2遊び手 → 統計（情報の移動）ストアレビューを定期取得し、種類（不具合・要望・称賛・離脱理由）に仕分けて件数を数える各ストアのレビュー取得 API、仕分けは Jev仕分けの種類を決める
3統計 → リスク・抽象モデル（解釈）新しい素材を読み、リスク と各モデルページへの追記案を書くClaude の週次ルーティン提案を確定するか決める
4開発 → ADR（集積）コミット履歴から「状況・何をしたか・なぜ」のカードを下書きするgit の差分＋Claude（セッション終了時のフック、または日次）なし（カードは記録なので確定不要）
5ADR → リスク・抽象モデル（解釈）ADR を5つの観点（リスク低減度・時間的般化・空間的般化・独特度・マネタイズ貢献度）で採点し、高いものを全体のモデルへの提案に回す採点は Jev（点数を返す判定が得意）、提案文は Claude提案を確定するか決める
6抽象モデル → 形式化（翻訳）確定したモデルから、Skill・フック・CLAUDE.md の規則の案を作るClaude案を採用するか決める
7モデル・ADR → 開発（適応）作業を始めるとき、そのプロジェクトに当てはまる確定済みのモデルとリスクを自動で読み込ませるClaude Code の SessionStart フックなし
8保管庫の点検孤立ノート・切れたリンク・重複・矛盾・古い記述を探して直すClaude の週次ルーティン正本の判断に迷うものだけ決める

導入の順番

順処理理由
1#4 ADR の下書き素材がすでに手元（git 履歴）にあり、外部 API の準備が要らない
2#7 適応の自動読み込み確定したモデルが1つでもあれば効果が出る
3#1・#2 ストアの数値とレビューAPI の認証準備が要る。数値の正本の問題（リスク）もこれで解消する
4#5 ADR の採点ADR がある程度溜まってから意味を持つ
5#3・#6・#81〜4 が回り始めてから

前提として決まっていないこと

  • Cloud Save から何を数えるか（#1 の「情報圧縮」の中身）
  • Jev を使う場合の API キーと費用の上限
  • 定期実行を GitHub Actions と Claude の定期ルーティンのどちらで動かすか
